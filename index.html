What changed, and what Lean checks

The completed Caliper routes derive reduction time, stored-code and total-memory bounds from local attacker and primitive implementations. They include lazy queries, initialization and extraction. Their asymptotic corollaries derive polynomial reduction resources from polynomial component bounds.

Shared random-oracle operations, algebraic state and results and Schnorr’s oracle interfaces keep the bookkeeping separate from each game’s winning condition. For BLS, OOPS and Proximity, the shared handler records explicit hash and signing replies; internal signer and verifier lookups do not add replies.

Separate Lean proofs establish eight exact equalities with the existing source experiments: seven security games and Proximity’s collision event. The adaptive state-encoding proof connects the new record fields to the original transcript representation.

Recorded local verification for this revision passed 2,008 Lean targets: 1,784 library modules and 224 regression modules. This is a Lean check of the recorded statements and implementations; agreement with the literature and independent security review remain separate.

Curve-specific primitive implementations and encoding contracts remain explicit. Conventional-machine and flat-memory adequacy remain separate refinements. Proximity’s game retains the fresh-collision event.

Schnorr ROM now has a checked first pass, fork-point selection, and restart and second execution retaining the first result, with time, code and memory bounds. Fresh-challenge rejection, matching the second fork slot, extraction and the public ROM statement migration still need to be joined.

An algebraic group model for VCVio

The AGM results above rest on agm-lean, a separate Apache-2.0 library that adds the algebraic group model to Lean 4 and VCVio. Other VCVio games can use it.

An algebraic adversary must explain every group element it sends as a combination of group elements it has already received. Having received g, X and Y, an adversary that sends a group element Z, in a query or in its final answer, also gives coefficients a, b, c with:

Z=a·g+b·X+c·Y

The library prescribes no game or oracle. Oracle replies need no explanation; they join the list of received inputs. The adversary supplies a Lean proof that its explanations hold on every possible reply path, and the library proves that running it yields valid explanations over the inputs it actually received.

Several groups can share one scalar field, as the two source groups of a pairing do. Each group element is explained only from inputs of its own group.

Key definitions

  • IsAlgebraic

    The explanation rule, required on every possible reply path.

  • Adversary

    A VCVio program paired with its proof of that rule.

  • Adversary.run

    Runs it through VCVio’s simulateQ, tracking each group’s received inputs.

  • Adversary.run_valid

    Every final explanation is valid over the inputs actually received.

The model does not bound running time or explain elements of a pairing’s target group. Games must keep every group element in the tracked group lists; group elements hidden in plain data go untracked. It starts from Fuchsbauer, Kiltz and Loss, The Algebraic Group Model and its Applications, Section 2.1.
